## Native iPhone and iPad interfaces

Apply this workflow to iOS and iPadOS interface tasks, across repositories. It does not require app edits for planning or read-only audits. Respect the app's deployment target, existing functionality, data contracts, privacy boundaries, and repository-specific instructions.

- Start with the current [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/) and the app's design system. Use `apple-ux-designer` for a new or revised flow, `adaptive-ipad-design` for layouts and multitasking, `ios-ux-auditor` for review, and `ios-conversion-optimizer` for a specific conversion problem.
- Prefer a polished native SwiftUI experience: native navigation and controls, SF Symbols with meaningful labels, restrained motion that respects Reduce Motion, and reusable components with semantic color, typography, and spacing tokens. Support light and dark appearances, Dynamic Type through accessibility sizes, VoiceOver reading order and actions, and a non-color cue for meaningful states.
- Design for the available window, not the device name. Keep iPhone navigation simple. On iPad consider sidebar/detail layouts, narrow split-screen windows, rotation, and keyboard navigation. Preserve selection and navigation state as the window changes.
- For Figma ↔ SwiftUI use the official Figma plugin's `figma-swiftui` skill. From Figma, inspect the selected frame, its screenshot, tokens, and component variants before implementing native behavior. From SwiftUI, use real view states and simulator captures to build editable Figma components in a designated file. Keep an explicit mapping between Figma variants and SwiftUI states. Do not treat a bitmap as an editable design or change a shared design without an authorized target.
- Use the official Build iOS Apps plugin and XcodeBuildMCP on a Mac with Xcode for runtime verification. Baseline existing behavior before changes. Run relevant existing tests and XCUITests for the changed flow and regressions. Compare actual iPhone and iPad simulator screenshots in light and dark mode, including a narrow iPad window and accessibility text sizes where relevant. Check VoiceOver and Reduce Motion separately; screenshots do not prove either. Report devices, tests, artifacts, and any checks not run. Never substitute a mockup for simulator evidence.
- On Windows, use the relevant application's authorized GitHub macOS CI for tests and screenshot artifacts. The account's standalone [Apple simulator MCP diagnostic](https://github.com/biserd/NYCSchools-iOS/actions/workflows/apple-mcp-diagnostics.yml) can be launched from any working directory. It verifies the toolchain, not an application's UI, and does not provide an interactive Mac connection. Never use signing, release, or TestFlight workflows as a substitute for simulator checks.
